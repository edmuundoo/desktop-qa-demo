# Тестирование desktop-приложения с TCP-сервисом

Решение тестового задания: чек-лист из 15 пунктов, обоснование критичного
сценария и запускаемый автотест на Python с комментариями и assert.
Основной файл для оценки автоматизации: **test_signals.py**.

## Границы решения и допущения

Приложение, исходники и TCP-протокол работодателя не предоставлены.
Подготовлен самостоятельный демонстрационный стенд: PySide6-приложение,
TCP-сервис отдельным процессом и тест на pytest / pytest-qt.
Он демонстрирует подход, но не проверяет неизвестный продукт работодателя.
Использован пакет `PySide6-Essentials`: он содержит необходимые QtWidgets
и QtNetwork без дополнительных модулей полного пакета PySide6.

Целевая ОС задания — Linux, Python 3.11+. Также возможен запуск на macOS.
Для Linux нужны системные библиотеки Qt соответствующего дистрибутива.

Принятый протокол:

- сервис слушает `127.0.0.1:2001`;
- запрос обновления — `GET\n`;
- ответ — JSON-массив из 10 сигналов, завершённый `\n`, кодировка UTF-8;
- поля — `id`, `name`, `value`, `quality`, `time`;
- время передаётся строкой ISO 8601 в UTC;
- значение отображается с тремя знаками после запятой;
- каждый ответ — полный снимок, подключение само не запрашивает данные.

Обычный режим сервиса возвращает синусоиду. В тесте сервис получает два
заранее заданных снимка. Приложение работает внутри процесса pytest,
сервис — в отдельном процессе. TCP, обработка ответа и Qt-виджеты настоящие.
Режим `offscreen` не проверяет работу оконного менеджера и визуальный рендеринг
на пользовательском рабочем столе. Запуск отдельного executable, установщик
и особенности приложения на C++/Qt не покрыты. Для внешнего C++/Qt-приложения
нужен другой способ управления интерфейсом; этот тест нельзя перенести без адаптации.

## Чек-лист

Это план проверок, а не заявление об их прохождении. Критерии, которых нет
в исходном условии, предложены для согласования с командой.

1. Запуск: окно открывается, есть пять колонок и кнопки «Подключиться», «Обновить», нет падения.
2. Подключение к доступному сервису на порту 2001: состояние подключения видно, обновление доступно.
3. Недоступный сервис: понятная ошибка, интерфейс отзывчив, возможна новая попытка.
4. Обновление до подключения: запрос не отправляется, приложение не падает.
5. Два последовательных обновления: все 10 сигналов и все пять полей соответствуют каждому снимку; нет дублей, пропусков и старых данных.
6. Изменение порядка сигналов: значения и метаданные остаются связаны с правильными ID.
7. Числа: корректно отображаются отрицательные, нулевые, дробные значения и границы согласованного диапазона.
8. Изменение качества: новое качество отображается у нужного сигнала, недостоверные данные не выдаются за достоверные.
9. Время: соблюдаются согласованные формат, часовой пояс и точность; новый снимок отличим от старого.
10. TCP-фрагментация: ответ, пришедший частями, собирается полностью; неполный снимок не отображается как завершённый.
11. Быстрые повторные нажатия «Обновить»: нет зависания, дублей и перезаписи нового снимка старым.
12. Задержка или отсутствие ответа: интерфейс отзывчив, по таймауту видна ошибка; старые данные не воспринимаются как успешно обновлённые.
13. Обрыв соединения: потеря связи видна; после восстановления сервиса можно подключиться и получить новые данные.
14. Некорректный ответ: повреждённый JSON, отсутствующие поля, повторяющиеся ID и неверные типы не вызывают падение или частичное обновление таблицы; ошибка диагностируема.
15. Закрытие и повторный запуск: соединение освобождается, приложение не зависает и снова подключается после запуска.

## Самый критичный сценарий

Выбран пункт 5: **корректность двух последовательных обновлений**.
Основное назначение приложения — показывать значения сигналов.
Незаметно неверные или устаревшие данные могут привести к ошибочным действиям
оператора даже при работающем соединении. Конкретную критичность и последствия
следует подтвердить с владельцем реального продукта.

Первый снимок проверяет начальное заполнение таблицы. Второй — изменение
значений, качества и времени без сохранения старых данных. Во втором ответе
порядок сигналов обратный: проверка сопоставляет строки по ID, не по позиции.
Ожидания задаются тестом и передаются симулятору через JSON-файл. Тест не
использует парсер приложения для вычисления ожидаемого результата.

Тест нажимает кнопки событиями мыши Qt, ждёт завершения операции без `sleep`,
читает текст ячеек и сравнивает все поля с ожидаемыми. Дубли ID проверяются
до преобразования в словарь. Процесс сервиса убирается даже после ошибки.
В Allure отображаются шаги теста, ожидаемые данные, фактический текст таблицы,
скриншоты после обновлений и журнал сервиса. При падении проверки
скриншот также сохраняется в `artifacts/failure.png`.

## Установка и запуск

Все команды выполнять из папки проекта.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
QT_QPA_PLATFORM=offscreen python -m pytest -v --alluredir=allure-results --clean-alluredir
```

`requirements.txt` задаёт диапазоны совместимых версий.
`requirements-tested.txt` фиксирует версии фактически проверенного окружения;
его можно использовать вместо `requirements.txt` для воспроизведения.

В графической сессии:

```bash
python -m pytest -v --alluredir=allure-results --clean-alluredir
```

Для ручной проверки в двух терминалах с активированным окружением:

```bash
python simulator.py
```

```bash
python app.py
```

Нажать «Подключиться», затем «Обновить». При следующих обновлениях значения меняются.
Порт 2001 должен быть свободен. Перед тестом остановить ручной симулятор.
Параллельный запуск тестов с фиксированным портом не поддерживается.
При ошибке запуска сервис выводит журнал в сообщении pytest.

Для будущего запуска в GitLab добавлен `.gitlab-ci.yml`: Linux-контейнер,
системные библиотеки Qt, offscreen-тест и отдельное задание сборки Allure-отчёта.
Pipeline ещё не выполнялся. HTML и исходные результаты сохраняются как артефакты,
в том числе при падении теста; код завершения pytest определяет результат тестового задания.
Конфигурация рассчитана на размещение файлов проекта в корне репозитория.

## Allure-отчёт

Для генерации HTML установлен проектный Allure Report 3 из npm.
Нужен Node.js (для CI выбран Node.js 22 LTS);
Java не требуется. Python-плагин `allure-pytest` уже включён в зависимости.
Версии npm-зависимостей закреплены в `package-lock.json`.

После выполнения теста:

```bash
npm ci --ignore-scripts --no-audit --no-fund
npm run report
```

Готовый отчёт находится в `allure-report/index.html`.
Это самостоятельный HTML-файл: его можно открыть в браузере или передать вместе
с архивом. Он содержит вложения и не требует сервера. Также доступна команда:

```bash
npm run report:open
```

`--clean-alluredir` очищает результаты предыдущего запуска, чтобы они не
смешивались с новым. Исходные результаты сохраняются в `allure-results/`.
Генерация отчёта не меняет результат выполнения pytest.

Документация: https://allurereport.org/docs/v3/install/
и https://allurereport.org/docs/pytest/.
